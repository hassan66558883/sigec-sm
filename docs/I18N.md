# Internationalisation — Francais (defaut) / Arabe

SIGEC-SM supporte le francais (langue par defaut) et l'arabe, les deux langues
officielles du Tchad. Pas de restructuration des routes (pas de `/fr/...`
`/ar/...`) : la langue est une **preference stockee dans un cookie**, lue au
rendu par les Server Components qui l'implementent. Ce choix delibere evite de
toucher aux dizaines de chemins absolus deja codes en dur dans l'application
(`redirect("/admin")`, `proxy.ts`, tous les `<Link href="/admin/...">`), qui
auraient tous du etre re-verifies si les routes avaient ete prefixees par
langue.

## Architecture

- `src/lib/i18n/config.ts` — locales supportees (`fr`, `ar`), langue par
  defaut, liste des locales RTL, nom du cookie.
- `src/lib/i18n/messages/fr.ts` / `ar.ts` — dictionnaires de traduction
  (memes cles dans les deux fichiers, verifie par le typage TypeScript :
  `ar.ts` importe le type `Dictionary` derive de `fr.ts`, donc une cle
  manquante ou un type different casse la compilation).
- `src/lib/i18n/translate.ts` — partie **client-safe** (aucun import de
  `next/headers`) : type `Dictionary`, fonction `makeT(dict)` qui resout une
  cle en chaine traduite avec interpolation `{variable}` simple. A importer
  depuis n'importe quel composant, serveur ou client (`"use client"`).
- `src/lib/i18n/server.ts` — partie **serveur uniquement** (lit le cookie via
  `next/headers`) : `getLocale()`, `getDictionary(locale)`, `getI18n()`. A
  importer uniquement depuis des Server Components / Route Handlers — jamais
  depuis un fichier `"use client"` (next/headers y provoquerait une erreur de
  build).
- `POST /api/locale` — change la langue (ecrit le cookie, 1 an, `sameSite=lax`,
  aucune permission requise : ce n'est pas une donnee sensible).
- `src/components/language-switcher.tsx` — bouton FR/عربي (Client Component),
  appelle `/api/locale` puis `router.refresh()`.

## RTL (arabe)

`<html>` racine (`src/app/layout.tsx`) reste fixe en `lang="fr"`, **sans**
attribut `dir` dynamique — volontairement, car une seule partie de
l'application est traduite (voir "Perimetre" ci-dessous). Si `dir="rtl"`
etait applique globalement, les pages pas encore traduites (toujours en
francais) s'afficheraient de droite a gauche, ce qui casserait leur mise en
page sans rien traduire.

A la place, chaque zone traduite pose son **propre** `dir={dir}` local (CSS
`direction` est heritable depuis n'importe quel element, pas seulement
`<html>`) :
- La page de connexion (`src/app/login/page.tsx`) sur son conteneur racine.
- La barre laterale admin (`src/app/admin/layout.tsx`) sur `<aside>`.
- Le tableau de bord principal (`src/app/admin/page.tsx`) sur son conteneur
  racine.

Les champs email/mot de passe du formulaire de connexion gardent `dir="ltr"`
explicite meme en arabe (convention universelle : adresses email et mots de
passe se saisissent toujours de gauche a droite). Les horodatages (`<time>`)
gardent aussi `dir="ltr"` (les chiffres/dates restent lisibles LTR par
convention, meme dans un contexte RTL).

**Limite connue** : les elements decoratifs positionnes en absolu par
coordonnees physiques (ex. les degrades flous en coin de `PageHero`, `left`/
`right`) ne s'inversent pas automatiquement avec `dir="rtl"` (contrairement a
`flex-row`, qui suit nativement le sens d'ecriture). Effet purement
cosmetique, pas fonctionnel — a corriger avec des utilitaires Tailwind
logiques (`start-`/`end-`) si besoin dans une prochaine passe.

## Perimetre livre (phase 1)

Traduits : page de connexion, coquille admin (barre laterale + pied de page +
notifications/changement de mot de passe/deconnexion), tableau de bord
principal (`/admin`).

**Non traduits** (restent en francais quelle que soit la langue choisie) : les
~25 pages de modules metier (citoyens, naissances, mariages, finances,
foncier, urbanisme, associations, plaintes, TECHNOTCHAD...) et le portail
citoyen (`/portail`). Choisir l'arabe ne traduit donc que la coquille et le
tableau de bord ; naviguer vers un module traduit pas encore fait retomber en
francais (LTR) pour cette page — comportement attendu, pas un bug.

## Etendre la traduction a une nouvelle page

1. Ajouter les cles necessaires dans `messages/fr.ts` **et** `messages/ar.ts`
   (TypeScript refuse de compiler si une cle manque dans l'un des deux).
2. Server Component : `const { locale, dir, t } = await getI18n();` (import
   depuis `@/lib/i18n/server`), poser `dir={dir}` sur le conteneur racine de
   la page.
3. Client Component : recevoir `dict: Dictionary` en prop depuis le parent
   serveur, puis `const t = makeT(dict);` (import depuis
   `@/lib/i18n/translate` — jamais depuis `@/lib/i18n/server`).
